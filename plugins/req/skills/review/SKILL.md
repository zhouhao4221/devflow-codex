# 需求评审

执行模型：按[命令模型路由](../../shared/_command-models.md)中 `req:review` 的档位执行；已作为执行子代理时不再次路由。

提交需求评审或记录评审结果。

> **Audience:** Product Manager
> 存储路径和缓存同步规则见 _storage.md（按需读取 [_storage.md](../../shared/_storage.md)）

## 命令格式

```
/req:review [REQ-XXX] [pass|reject]
```

- 省略编号时自动选择「草稿」「评审驳回」或「待评审」的需求
- 多个候选时让用户选择

## 执行流程

### 根据当前状态执行不同操作

---

## 场景一：提交评审（草稿/评审驳回 → 待评审）

当需求状态为「草稿」或「评审驳回」时：

### 1. 完整性检查

提审检查需求定义是否足以评审，按[需求模板](../../templates/requirement-template.md)区分需求阶段与开发阶段。结合需求类型检查实际内容，不把所有模板章节都当作提审必填项：

| 检查项 | 提审要求 |
|--------|----------|
| 需求描述 | 背景、目标与范围清楚，能理解要解决的问题 |
| 功能清单 | 有具体功能点；未勾选表示尚未实现，不代表未填写 |
| 业务规则 | 涉及的校验、权限、状态或其他约束明确 |
| 数据与交互 | 后端/全栈检查接口能力及业务输入输出；前端检查页面交互与数据需求，不强求具体接口设计 |
| 测试要点 | 有可观察的场景、预期结果或验收标准；不要求测试已执行或手动用例已生成 |

- 需求阶段必需内容只有标题、模板示例或待补充占位时，列为缺失；有依据的不适用项可跳过，不要求为凑齐章节编造内容。
- **实现方案不属于提审门槛**：数据模型、API 设计、文件改动清单、实现步骤由 `/req:dev` 分析代码后生成。空白或 `_开发阶段填充_` 均不阻塞提审，旧版文档中这些内容单独成章也同样处理，不要求先执行 `/req:edit` 或 `/req:dev` 补齐。
- 图示等可选内容、评审记录和开发/测试进度不作为提审必填项。已有实现方案可供参考，但不能据此要求其他需求提前填写。

```
需求完整性检查

✅ 需求描述 - 已填写
✅ 功能清单 - 3 个功能点
✅ 业务规则 - 5 条规则
✅ 接口需求 - 3 个接口能力
✅ 测试要点 - 8 个测试点
⏭ 实现方案 - 开发阶段生成，不影响提审

检查结果：✅ 通过
```

仅当需求阶段必需内容缺失时停止，保持当前状态，列出具体缺项与原因，并提示编辑后重新提审：
```
❌ 需求完整性检查失败

缺失内容：
- ❌ 业务规则 - 未填写
- ❌ 测试要点 - 没有场景与预期结果

请先完善需求文档：/req:edit REQ-XXX
```

### 2. 生成评审摘要

检查通过后继续生成摘要并更新状态。摘要只引用需求文档或已核实的信息；尚无实现方案时，文件数、表结构、技术工作量标为「开发阶段确认」或省略，不为生成摘要提前分析代码或编造数量。

```markdown
## 需求评审摘要

### 基本信息
- 编号：REQ-001
- 标题：部门渠道关联
- 优先级：P1
- 功能点数：6

### 需求概述
在组织部门管理中，实现部门和分组与渠道的关联功能...

### 影响范围
- 模块：sys（系统）、oms（订单）、dashboard（看板）
- 文件数与表结构：开发阶段确认

### 风险评估
- 中等风险：涉及权限控制逻辑变更

### 工作量评估
- 功能点：6 个
- 技术工作量：开发阶段确认
```

### 3. 更新状态并同步缓存

- 修改元信息状态为「待评审」
- 勾选生命周期「待评审」
- **同步到主仓需求目录**

### 4. 提示

```
✅ 需求已提交评审

REQ-001 部门渠道关联
状态：待评审

评审通过后执行：/req:review REQ-001 pass
评审驳回执行：/req:review REQ-001 reject
```

## 场景二：评审通过（待评审 → 评审通过）

当参数包含 `pass` 时：

### 1. 状态检查

```
if 状态 != "待评审":
    错误：当前状态不是「待评审」，无法执行评审操作
    退出
```

### 2. 收集评审信息

```
评审人：<git config user.name 的值>（如需修改请输入）
评审意见：（可选）
```

- **评审人**（必填）：默认取 `git config user.name`，展示给用户确认，用户可修改
- **评审意见**：可选

### 3. 记录评审结果并同步缓存

- 更新「评审记录」章节
- 修改元信息状态为「评审通过」
- 勾选生命周期「评审通过」
- **同步到主仓需求目录**

### 4. 提示

```
✅ 评审通过

REQ-001 部门渠道关联
状态：✅ 评审通过

开始开发：/req:dev REQ-001
```

---

## 场景三：评审驳回（待评审 → 评审驳回）

当参数包含 `reject` 时：

### 1. 收集评审信息

```
评审人：<git config user.name 的值>（如需修改请输入）
驳回原因（必填）：
```

- **评审人**（必填）：默认取 `git config user.name`，展示给用户确认，用户可修改
- **驳回原因**（必填）：必须填写

### 2. 记录评审结果并同步缓存

- 更新「评审记录」章节（驳回原因必填）
- 修改元信息状态为「评审驳回」
- **同步到主仓需求目录**

### 3. 提示

```
❌ 评审驳回

REQ-001 部门渠道关联
状态：❌ 评审驳回

驳回原因：接口需求需要补充异常场景说明

修改需求：/req:edit REQ-001
重新提审：/req:review REQ-001
```
