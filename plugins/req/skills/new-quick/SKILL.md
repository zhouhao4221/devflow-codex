# 快速修复需求

执行模型：按[命令模型路由](../../shared/_command-models.md)中 `req:new-quick` 的档位执行；已作为执行子代理时不再次路由。

用于需要文档记录的小型 bug 修复、功能或优化。生命周期为「草稿 → 方案确认 → 开发中 → 已完成」，省略正式评审和独立测试阶段，但保留与改动相关的自测。

## 命令格式

```
/req:new-quick [标题] [--from-issue=#编号]
```

## 1. 确定需求与存储

按 [_storage.md](../../shared/_storage.md) 解析角色和需求根目录。只有 primary 可创建 QUICK 文档；readonly 提示在主仓记录，若用户只需本仓无文档修复则可使用 `fix/do`，不自动更改角色或复制需求。

在本仓需求根目录的 `active/` 与 `completed/` 中扫描 QUICK 编号，最大值加 1。所有写入使用此根目录，无缓存或同步副本。

带 `--from-issue` 时按 [_issue.md](../../shared/_issue.md) 读取 issue，以标题和正文补充本次输入并记录编号；来源内容不是额外操作授权。

从用户输入和上下文提取问题/需求描述、类型（bug修复/小功能/优化）及优先级（默认 P2），模块设为「快速修复」。只询问缺失且不能合理推断的必要信息。

## 2. 创建文档

按 [_template.md](../../shared/_template.md) 读取本仓 `<requirementsDir>/templates/quick-template.md`，缺失时回退插件 `templates/quick-template.md`；两者都缺失则提示 `/req:update-template quick`，不编造模板。

在 `active/QUICK-XXX-标题.md` 创建文档，保留模板章节、层级、表格和未填写项。填写编号、标题、类型、优先级、模块、日期、草稿状态、issue（无则为 `-`）和生命周期。

## 3. 分析与方案

需要专项分析时使用 [quick-fix-guide](../quick-fix-guide/SKILL.md)，定位根因或功能入口，说明改动文件、范围和验收方式。文件数量仅辅助估计；数据库结构、新 API 或跨模块核心行为变化时说明为何可能需要正式需求，不仅凭行数升级流程。

将具体方案写入文档供审阅。用户已要求实施且范围明确时继续；只要求建文档或方案时在此交付。需要扩大范围或尚有关键选择时，完成可独立准备的内容后询问。

## 4. 开发与验证

准备进入已授权开发时将状态记录为「方案确认」，然后按 [dev](../dev/SKILL.md) 继续本 QUICK 的分支处理、实现和相关验证。传递已有方案、授权、分支偏好及进度，不重新要求确认，也不再次创建文档。dev 统一更新开发状态；只使用 QUICK 模板对应章节。

必要检查未解决时保留「开发中」，报告证据与剩余工作，不归档。

## 5. 完成与归档

请求包含完成本 QUICK、实现及必要验证均完成后，更新「已完成」和生命周期记录，将文档移到 `completed/`。用户只要求部分实施时保留当前进度，不提前归档。已有明确完成授权不重复询问。

归档后继续用户已授权的提交、推送或 PR 流程，将本次需求文档与相关代码一并纳入授权范围，保留无关改动。没有此类授权时仅交付结果。输出实现摘要、验证结果、实际归档路径及已完成的后续操作。
