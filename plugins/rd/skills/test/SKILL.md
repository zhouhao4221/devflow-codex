# 需求测试

执行模型：按[命令模型路由](../../shared/_command-models.md)中 `rd:test` 的 `primary` 档执行；已作为执行子代理时不再次路由。交互走查和最终验收留在当前主会话，不交给经济档测试执行者；保留用户当前选择的模型，不因工具缺失静默换模型。

针对指定需求执行综合测试：运行已有测试 → 引导创建新测试 → 自动走查可交互验证的测试要点。

> 存储路径规则见 [`_storage.md`](../../shared/_storage.md)

## 命令格式

```
/rd:test [REQ-XXX|QUICK-XXX] [选项]
```

省略编号时自动选择「开发中/测试中」的需求，多个候选让用户选择。

| 选项 | 说明 |
|-----|------|
| `--failed` | 仅运行上次失败的测试 |
| `--skip-ut` / `--skip-api` / `--skip-e2e` | 跳过对应阶段 |
| `--skip-walkthrough` | 跳过交互走查 |
| `--force` | 某阶段失败时继续后续 |

---

## 总体流程

1. 选择需求 & 前置检查（状态必须为「开发中/测试中」，功能未完成时警告）
2. REQ 提取「测试要点」，QUICK 提取「验证方式」；再按 API、业务规则、数据权限和其他维度组织
3. 识别变更范围（优先需求文档「文件改动清单」，否则 `git diff`，按 testing.md 定位测试文件）
4. **阶段一：UT** — 回归运行变更相关已有 UT（委派 `test-runner`）→ 缺失时引导 `/rd:test-new --type=ut`
5. **阶段二：API 测试** — 按 testing.md 启动环境 → 回归已有（委派 `test-runner`）→ 缺失时引导 `/rd:test-new --type=api`
6. **阶段三：E2E 测试** — 额外检查前端服务 → 回归已有（委派 `test-runner`）→ 缺失时引导 `/rd:test-new --type=e2e`
7. **交互走查** — 对自动化未覆盖的测试要点探测当前 UI 控制能力；可执行时自动走查，否则生成手动验证清单
8. 验证结果符合门槛时更新状态为「测试中」并记录结果；直接写主仓需求目录，不做缓存同步
9. 汇总报告（各阶段通过/失败、测试要点覆盖率）

全部通过 → 提示 `/rd:done`。存在失败 → 列出失败用例和原因，提示 `/rd:dev` 修复或 `--failed` 重跑。

QUICK 使用同一条测试命令和状态流。不在 QUICK 文档插入 REQ 专属章节；记录实测项的证据。暂无法实测的项写为 `- [ ] 事项（待观察：原因）`，并在报告中列为未验证。

## 回归阶段的执行方式

阶段一~三的「回归运行已有测试」按日志规模和任务独立性决定是否委派给 `test-runner`，主会话只接收摘要，测试日志不进入主会话；规则见 [`_delegate.md`](../../shared/_delegate.md)。

- 环境检查/启动（阶段二、三）仍由主会话完成，subagent 只跑测试命令
- prompt 自包含：工作目录、testing.md 中的运行命令（已拼好 `--failed`/模块过滤）、本阶段要跑的测试文件清单、`--failed` 模式下的上次失败清单
- 同一阶段内可按文件/模块拆分且不存在共享数据库、端口或可写 fixture 冲突时，可并行派发；否则串行或先隔离环境
- subagent 回传 ERROR（依赖缺失、命令不存在、编译失败）时按原因处理或询问用户，不要改命令绕过
- 汇总结果按 [统一证据契约](../../shared/_evidence.md) 核对覆盖范围与当前输入；依据一致的结果直接复用，输入变化或依据缺失时补跑受影响检查。任务 DONE 不代表测试 PASS

## 交互走查

阶段七只处理自动化尚未覆盖且需要真实界面确认的测试点；`--skip-walkthrough` 时跳过，`--failed` 时只重跑上次失败或未完成的走查项。若项目已有匹配的 `docs/uat/flows/<module>.md`，复用其中的场景和证据格式；否则从需求测试点生成本次临时步骤，不为一次走查擅自创建持久 UAT 文档。

### 能力探测与工具选择

1. 检查当前会话实际暴露的 UI 控制工具及其说明，不通过环境变量、进程名或插件目录推断“是否 Codex 桌面端”。若工具要求先读取应用、浏览器或标签页清单，严格按其文档执行初始化调用，再根据返回的可用表面继续。
2. 用户明确指定的应用、浏览器或标签页优先。否则：需要现有登录态、Chrome 标签页或扩展时选 Chrome；localhost 或无需登录且适合隔离会话的 Web 页面选内置浏览器；原生桌面应用或跨应用流程选 Computer Use。
3. 目标表面不存在、工具不可调用、权限未授予或模型不支持该工具时，记录具体原因并降级为逐项手动验证，不把“运行在桌面端”等同于能力可用。

### 执行与证据

- 交互走查由 `primary` 主会话串行执行；测试命令与大段日志仍可按 [_delegate.md](../../shared/_delegate.md) 交给 `test-runner`。不要让多个任务同时操作同一应用、浏览器配置或测试账号。
- `/rd:test` 只授权在已确认的测试环境和测试数据范围内完成测试步骤。目标可能是生产环境，或步骤涉及发送、发布、购买、删除真实数据等难以恢复的外部操作时，先取得明确授权；未获授权则只验证到动作前并记录阻塞点。
- 每个测试点记录执行模型、工具/表面、关键操作、预期、实际与 PASS/FAIL/MANUAL。失败时保留最小充分证据（截图、页面状态、Console Error 或命令日志）；无法自动执行的项目不得记为通过。
- UI 操作失败先区分页面、权限、环境与工具错误。环境或工具错误不触发模型升级；确属复杂行为判断时由主会话补充分析，最终结论仍以实际断言证据为准。

## 测试模式

| 模式 | 命令 |
|------|------|
| 综合测试（默认） | `/rd:test REQ-XXX` |
| 增量测试 | `/rd:test REQ-XXX --failed` |
| 跳过阶段 | `--skip-ut` / `--skip-api` / `--skip-e2e` |
| 跳过交互走查 | `--skip-walkthrough` |
| 强制继续 | `--force` |
