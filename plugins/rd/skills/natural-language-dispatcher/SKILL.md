# 自然语言需求调度器

解析用户自然语言意图，映射到对应命令。本技能只做**意图识别与命令映射**，解析完成后读取对应技能文件按原流程执行。

> 唯一例外：§七「确认偏好开关」不对应任何命令，由本技能直接执行文件动作。

---

## 编号解析规则

| 输入 | 解析 |
|------|------|
| `REQ-025` / `REQ025` | REQ-025 |
| `QUICK-003` / `QUICK003` | QUICK-003 |
| 纯数字 `025` / `3` | REQ-XXX（补零到 3 位） |
| `#42` / `issue 42` | issue `#42`，映射为 `--from-issue=#42` |

纯数字默认 REQ。当前分支暗示 QUICK（如 `fix/QUICK-XXX-...`）时优先 QUICK。无法确定时询问。

## 一、需求文档操作

### 新增需求 → `/rd:new`

触发："新增需求"、"新建需求"、"创建需求"（不要求编号，系统自动生成）。

提取字段：标题、类型（`--type`）、模块（`--module`）、issue（`--from-issue`）。

### 修改需求 → `/rd:edit`

触发："修改/编辑/变更需求" + 编号（缺编号不触发）。

---

## 二、修复与开发（无文档）

### 修 bug → `/rd:fix`

触发："修/修复/修一下" + "bug/问题/报错/异常/错误" + 具体描述。

仅当用户显式传入 `--auto`，或明确要求修复后提交并推送创建 PR 时，映射为 `/rd:fix --auto`。"一键修"、"自动修"、"不用确认"只影响已授权修复的交互，不增加提交、推送或 PR 授权；只要求其中部分操作时逐项传递授权，不用 `--auto` 补齐其他操作。用户和项目已有的分支、提交及 PR 偏好持续有效。

不触发：提问/讨论语气（"这个 bug 怎么修"）。

### 优化/重构/升级 → `/rd:do`

触发：祈使语气动词（优化、重构、升级、统一、整理、抽取、迁移）+ 具体对象。

不触发：讨论语气（"可以优化"）、无对象（"优化一下"）。

### 快速需求文档 → `/rd:new-quick`

用户明确要求创建 QUICK / 快速需求文档时使用。单纯"快速修复"走 `/rd:fix`，"加个小功能"走 `/rd:do`；任务规模和"快速"措辞本身不代表要求创建文档。

## 三、需求状态流转（必须带编号）

| 自然语言 | 映射 |
|---------|------|
| "开发/开始开发" + 编号 | `/rd:dev` |
| "测试/开始测试" + 编号 | `/rd:test` |
| "评审通过" + 编号 | `/rd:review pass` |
| "评审驳回/驳回" + 编号 | `/rd:review reject` |
| "完成/归档/做完了" + 编号 | `/rd:done` |

## 四、版本与 PR 操作

| 自然语言 | 映射 |
|---------|------|
| "规范提交"、"提交代码" | `/rd:commit` |
| "创建 PR"、"提 PR" | `/rd:pr` |
| "审 PR"、"审查 PR" | `/rd:pr review` |
| "合并 PR" | `/rd:pr merge` |
| "拉 PR 评论"、"处理 PR 反馈" | `/rd:pr comments` |

仅用户显式指定 `review --auto` 或明确授权发布审查评论时传入 `--auto`。"自动审查"、"不用确认"仍只输出审查结果，不授权评论或合并；"提交"对象不清时先完成审查，再澄清外部操作。

> `merge` 和 `fetch-comments` 各自交互点不走 `--auto`。

## 五、Issue 操作

| 自然语言 | 映射 |
|---------|------|
| "提/建/开 issue: <标题>" | `/rd:issue new <标题>` |
| "给 #N 回复/评论 <内容>" | `/rd:issue comment N <内容>` |
| "关闭/close issue N" | `/rd:issue close N` |
| "重开/reopen issue N" | `/rd:issue reopen N` |
| "看下 issue N" | `/rd:issue show N` |
| "列出 issue" | `/rd:issue list` |

编辑类："给 issue N 加标签 X" → `/rd:issue edit N --add-labels=X`

## 六、Git 平台 URL 识别

### 识别模式

支持完整 URL 和纯路径：`owner/repo/issues/N`、`owner/repo/pulls/N`。`pull` 和 `pulls` 均识别为 PR。

### 仓库匹配

解析 `owner/repo` 与 `git remote get-url origin` 对比。不匹配则提示切换仓库，不跨仓库执行。

### Issue URL

- **仅 URL**（无动词）→ 展示操作选项（修 bug / 创建需求 / 快速修复 / 智能开发 / 查看 / 评论 / 关闭）
- **URL + 动词**（如"修 .../issues/169"）→ 直接映射到对应命令

### PR URL

从 URL 解析 PR 编号并获取实际元数据；审查按目标 PR 的 base/head 读取，不要求当前分支匹配或切换工作区。

- **仅 URL** → 展示选项（查看状态 / 审查 / 拉评论 / 合并）
- **URL + 动词** → 直接映射

### 优先级

动词 + URL > 仅 URL > 动词 + 需求编号

## 七、确认偏好开关

仅管理 DevFlow 的「提交前再次确认」偏好，不控制 Codex 原生权限弹框。用户要求改变原生审批时说明区别，不把 marker 状态当成环境权限状态。

用户明确要求持久化该 DevFlow 偏好时：开启则创建 `.devflow/.req-confirm-commit`，关闭则移除该文件，查询则读取其存在状态。已有文件仅代表偏好；当前会话的新指令优先。按需确保 marker 被 Git 忽略，不写跨项目 memory。没有持久化要求时仅在当前会话遵循偏好。

提交步骤按 [_template.md 的确认操作规范](../../shared/_template.md#确认操作规范) 执行；marker 不授予任何提交、推送或外部操作权限。

## 不触发的情况

- 查询/展示类："看一下025需求" → 走 `/rd:show`
- 讨论/提问："可以优化"、"怎么修"、"是不是该重构了"
- 缺必要信息："修改需求"无编号、"优化一下"无对象
- 涉及插件自身维护：修改模板、优化技能
- URL 指向其他仓库、非 issue/PR 路径、纯域名
- 用户消息以 `/rd:` 等斜杠命令开头

## 执行流程

1. **确认意图**：一行说明，如 `🧠 识别：/rd:fix 登录超时`
2. **读取对应技能文件**，按原流程执行
3. **传入解析出的参数**
4. **后续与原命令完全一致**

多意图按依赖顺序处理并传递各自授权；只有缺少必要信息或外部操作授权时询问。能从上下文确定的参数直接使用，不重复走已完成的交互。
