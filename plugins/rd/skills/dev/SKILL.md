# 需求开发

执行模型：按[命令模型路由](../../shared/_command-models.md)中 `rd:dev` 的档位执行；已作为执行子代理时不再次路由。

根据需求和已有实现推进到本次请求的完成条件。普通开发包含实现、相关验证和失败修复；用户只要求方案或限定某部分工作时遵循该范围。

## 命令格式

```
/rd:dev [REQ-XXX|QUICK-XXX] [--reset]
```

省略编号时从上下文或可开发需求中选择；多个无法区分的候选才询问。`--reset` 重新生成实现方案，不清除代码或已有工作。

## 1. 需求与状态

按 [_storage.md](../../shared/_storage.md) 解析需求根目录。primary 可更新本仓需求文档；readonly 直读主仓，可实施本仓代码，但不创建、复制或回写需求文档。

| 类型 | 当前状态 | 处理 |
|------|----------|------|
| REQ | 草稿、待评审、评审驳回 | 提示先完成评审，不进入实现 |
| REQ | 评审通过、开发中、测试中 | 开始或继续开发 |
| QUICK | 草稿、开发中 | 在请求授权范围内开始或继续；方案确认记录于开发记录，不是独立状态 |
| 任一 | 已完成 | readonly 可基于它开发；primary 提示已完成，新增需求范围应另行记录 |

读取需求定义、实现方案和已有进度，核对实际代码。继续开发时复用仍有效的方案和验证证据，不重新询问已确认内容。

## 2. 工作区与分支

先查看 `git status --porcelain` 和相关 diff，区分本次需求的已有实现与用户无关改动。可在当前分支继续时保留这些改动并推进；只有待执行的切换可能覆盖改动、归属不清且影响编辑，或发生实际冲突时才暂停相关操作。不得自动 stash、重置、删除或提交用户的无关改动。

用户和项目 AGENTS.md 的明确分支约定优先。已授权直接使用主分支时留在约定分支；readonly 不因需求元信息切换分支。其余 primary 工作按 [_branch.md](../../shared/_branch.md) 执行：

- 需求已有 `branch`：当前分支匹配则继续；需要切换时先核实本地或远端引用。多个分支从任务上下文选择，无法确定才询问。已记录分支不存在时核实是否已合并或改名，不静默重建同名分支。
- 首次开发需要新分支：从配置的 `branchFrom` 创建，REQ 用 `featurePrefix`，QUICK 用 `fixPrefix`；默认前缀为 `feat/` 和 `fix/`。名称包含需求编号及最多 5 个英文词的 kebab-case slug；有关联 issue 时追加 `-iN`，见 [_issue.md](../../shared/_issue.md#issue-与分支提交的关联)。展示实际基准和名称，在已有授权内执行后记录 `branch`。
- 未配置基准时依次核实远端默认分支、`origin/main`、`origin/master`。无法确定时询问基准，不猜测或顺便迁移主分支。

## 3. 方案与上下文

按任务涉及的模块、架构边界和接口查阅项目资料。需要项目类型对应的方案细节时读取 [dev-guide](../dev-guide/SKILL.md)；无需重复加载已读资料。

先定位既有实现和受影响调用方。范围较大且存在独立定位任务时，按 [_delegate.md](../../shared/_delegate.md) 委派 `code-scout`；否则直接搜索并读取相关片段。

方案说明数据/接口变化、文件改动、实现依赖和验收方式。每个改动单元给出可执行命令或可观察行为；保持现有需求模板：REQ 写入「实现方案」对应小节，QUICK 使用简化模板的「实现方案」「验证方式」，不强加 REQ 章节。

已有完整方案且仍符合请求时复用；发现变化只补充差异。展示可审阅方案后继续已授权实施。缺少影响正确性的选择、需要扩大范围或用户要求先审阅时，完成可独立准备的内容再询问。只要求方案时交付方案并结束。

## 4. 实施与记录

primary 首次实施时更新为「开发中」，继续开发时保留状态；同步更新对应生命周期记录和方案，不写缓存。已有方案授权沿用，包括从 `new-quick` 进入的任务。

按实际依赖顺序实现。后端遵守项目分层职责，前端按交互功能组织；已稳定的跨层契约不要求人为串行。适合委派的独立单元按 [_delegate.md](../../shared/_delegate.md) 分配实现及对应测试，保留共享文件归属、接口依赖和主会话整合责任。无法委派时主会话继续完成。

核对实际 diff 与产物后更新实施清单。primary 同时更新文档中的进度，readonly 只更新当前会话清单。实现方案可按已授权改动同步调整；需求定义只改用户要求的内容，新增业务范围先说明并取得授权，修改后记录变更。保持文档模板结构。

## 5. 验证与完成

实现后执行 [_verify.md](../../shared/_verify.md) 的相关检查，修复本次变更造成的问题并重跑受影响范围；已有有效结果按 [_evidence.md](../../shared/_evidence.md) 复用。必要验证未解决时，报告当前产物、失败证据和剩余工作，不宣布开发完成。

交付摘要包含已实现行为、验证结果及实际未执行项。不要把运行必要检查推迟成「下一步执行 /rd:test」；独立业务验收或更广的测试阶段仍可留给 `/rd:test`。开发完成本身不自动归档需求。

由 `new-quick` 调用时将验证结果返回给调用流程，由它完成归档后统一处理后续操作。其他情况下，若用户还授权了提交、推送或 PR，继续对应流程；只有配置平台或关联 issue 不代表授权发布。按用户指定分支操作，不向禁止 PR 的用户追加 PR 流程。
