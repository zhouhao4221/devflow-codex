# 需求评审

执行模型：按[命令模型路由](../../shared/_command-models.md)中 `rd:req-review` 的档位执行；已作为执行子代理时不再次路由。

提交 REQ 需求评审（AI 先预审）或记录人工评审结果。代码审查不在这里：审 PR 用 `/rd:review`。

> **Audience:** Product Manager
> 存储路径和写入规则见 [_storage.md](../../shared/_storage.md)。
> 仅对 REQ 生效；QUICK 没有评审站，草稿即可 `/rd:dev`。
> `readonly` 仓库只展示预审意见，不写评审记录、不改状态。

## 命令格式

```text
/rd:req-review [REQ-XXX] [pass|reject] [--comment=评审意见]
```

- 省略编号时自动选择「草稿」、「评审驳回」或「待评审」的 REQ。
- 多个候选时让用户选择。

## 场景一：提交评审

当需求状态为「草稿」或「评审驳回」时执行。

### 1. 完整性检查

按[需求模板](../../templates/requirement-template.md)区分需求阶段与开发阶段。结合需求类型检查实际内容，不把所有模板章节都当作提审必填项：

| 检查项 | 提审要求 |
|--------|----------|
| 需求描述 | 背景、目标与范围清楚 |
| 功能清单 | 有具体功能点；未勾选只表示尚未实现 |
| 业务规则 | 涉及的校验、权限、状态或其他约束明确 |
| 数据与交互 | 后端/全栈检查接口能力及输入输出；前端检查页面交互与数据需求 |
| 测试要点 | 有可观察场景、预期结果或验收标准 |

- 只有标题、模板示例或待补充占位时视为缺失；有依据的不适用项可跳过。
- 实现方案由 `/rd:dev` 分析代码后生成，不属于提审门槛。
- 需求阶段必需内容缺失时停止，保持当前状态，列出具体缺项并提示 `/rd:edit REQ-XXX`。

### 2. AI 预审

读目标需求全文，再读 `active/` 与 `completed/` 下其它需求的标题、功能清单与范围；QUICK 只取标题与「问题描述」。从四个维度给出意见：

| 维度 | 关注点 |
|------|-------|
| 合理性 | 目标、功能清单、业务规则与接口需求是否相互覆盖且不矛盾 |
| 粒度 | 功能点是否过多、模块是否过散、是否应先 `/rd:split` |
| 冲突 | 与进行中或已完成需求是否重叠，是否修改同一规则而未提及 |
| 风险与遗漏 | 异常流程、测试覆盖、假设与依赖是否缺失 |

意见分为「阻塞」、「建议」、「信息」，每条附章节定位。预审只产出意见，不改需求定义章节的内容或结构。

- 有阻塞项：询问「预审有 N 项阻塞，仍要提审吗？(y/n)」。`n` 时保持状态并结束；`y` 时继续。
- 无阻塞项：直接继续。

在「八、评审记录」追加日期、评审人 `AI 预审`、结论（`提审` 或 `预审未提审`）和不超过 200 字的精简摘要。表中只有 `| - | - | - | - |` 占位行时，首条记录替换该行，不影响其它章节的同形占位。`readonly` 时跳过写入。

### 3. 生成评审摘要

摘要包含编号、标题、优先级、需求概述、功能点数、影响模块、关联需求、风险和 AI 预审计数。尚无实现方案时，文件数、表结构和技术工作量标为「开发阶段确认」或省略。带阻塞项仍提审时显式标记「⚠️ 带 N 项阻塞提审」。

### 4. 更新状态

仅 `primary` 仓库执行：将元信息状态改为「待评审」，勾选生命周期「待评审」。`readonly` 仓库只展示预审和摘要，说明未写入。

## 场景二：评审通过

参数包含 `pass` 时：

1. 要求当前状态为「待评审」，否则结束并说明。
2. 评审人默认取 `git config user.name`，展示给用户确认并允许修改；`--comment=` 作为可选评审意见。
3. 在「评审记录」追加一行，不覆盖 AI 预审记录。
4. 将状态改为「评审通过」并勾选对应生命周期，提示 `/rd:dev REQ-XXX`。

## 场景三：评审驳回

参数包含 `reject` 时：

1. 要求当前状态为「待评审」。
2. 评审人默认取 `git config user.name`；驳回原因必填，优先取 `--comment=`，缺少时询问。
3. 在「评审记录」追加一行，将状态改为「评审驳回」。
4. 提示先 `/rd:edit REQ-XXX`，再 `/rd:req-review REQ-XXX`。

## 状态流转

```text
草稿 ────提审────▶ 待评审 ──pass──▶ 评审通过 ──▶ /rd:dev
                     │  ▲
                 reject │ 重新提审（/rd:edit 后）
                     ▼  │
                   评审驳回
```

驳回后状态保持「评审驳回」，修改后重新提审直接进入「待评审」。
